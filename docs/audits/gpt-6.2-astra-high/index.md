# Project portfolio management audit for healthcare use

25 November 2026 · Source revision `43cd000e` on `mobile-apps` · Technical and product assessment for a health-board sponsor, portfolio office and engineering team.

## Decision

**Pilot the web application with one health-board portfolio office to manage a digital-service roadmap.** Start with approved project descriptions, dependencies, owners and review dates. The team can demonstrate value by reconciling its existing spreadsheet and preparing a board pack from the same records. The repository already contains a Digital Health and Care Wales (DHCW) roadmap mapping, example data, an import preview and conflict-aware publishing. Those are unusually good starting conditions for a measurable pilot. The mapping describes a potential integration. A live DHCW deployment or endorsement was outside the evidence reviewed. [Roadmap editor mapping](../../../operations/dhcw-roadmaps-editor.md) · [Import request tests](../../../project-portfolio-management-service-with-rust/tests/requests/dhcw_apply.rs)

**Defer reliance on PPM to authorise a clinical-system cutover.** A lead can sign an open decision, the supporting evidence can subsequently change, and the service can still count the earlier signature. After a difficult go-live, the approval record may therefore be unable to show which evidence the lead approved. This matters even when the portfolio contains no patient records. Make that the first engineering priority for any team proposing such a use. [Cutover controller](../../../project-portfolio-management-service-with-rust/src/controllers/cutover.rs) · [Cutover database rules](../../../project-portfolio-management-service-with-rust/migration/migrations/20261010000075_cutover_decisions.up.sql)

## What the project does well

- **A decision can already be stopped.** Criteria are published before a cutover opens. An empty, unmarked or failed set cannot support a go. A writer can record a no-go or a safety delay with a reason. The database guards published criterion wording and final decisions. The real-token request suite covers the refusal and success paths. Preserve the ability to stop immediately when improving the signing rules. [Domain rules](../../../project-portfolio-management-service-with-rust/domain/src/cutover.rs) · [Request tests, EX-6](../../../project-portfolio-management-service-with-rust/tests/organizations.rs)
- **The board can see uncertainty.** Financial benefits distinguish claimed and independently validated amounts, separate currencies, and distinguish recurring from one-off sums. A non-financial benefit without a usable KPI can show as unmeasured. The workforce bridge distinguishes current, previously received, withheld and unknown supply. These distinctions matter when deciding whether to fund expansion or whether staff have time to implement it. [Benefits controller](../../../project-portfolio-management-service-with-rust/src/controllers/benefit_validation.rs) · [Workforce readings and limits](../../../operations/wpm-bridge.md)
- **The architecture supports review of individual decisions.** The Rust service separates database writes from pure decision rules. The matcher explains its component scores. A keyless import that resembles an existing plan can be held for review. The SvelteKit client has browser tests for the cutover workflow, and the service has tests for what private plans contribute to aggregate views. These are good places to add healthcare-specific examples without introducing clinical records into the model. ## Findings and acceptance criteria

### 1. Make a cutover signature attest to the evidence used for the decision

The controller checks the signer's role and records the decision, role, actor and date. It permits evidence and the assessment of whether a criterion is met to change while the decision is open. The unique signature is per decision and role. The required roles come from current deployment configuration, including when the controller renders the decision. The final handler reads the criteria and signatures before starting its write transaction. Static inspection establishes the missing evidence binding. The concurrent outcome remains unverified. [Cutover controller, especially `view`, `mark`, `cosign` and `decide`](../../../project-portfolio-management-service-with-rust/src/controllers/cutover.rs) · [Signature schema](../../../project-portfolio-management-service-with-rust/migration/migrations/20261010000075_cutover_decisions.up.sql)

**Service owner and clinical change lead, before use for go-live.** Freeze the required roles when a decision opens. Bind each signature to a revision of the marked criteria and evidence, and show that revision and signing time in the decision pack. Validate and commit a go against one consistent revision. Where the board requires independent people, enforce that policy explicitly. Acceptance should cover changed evidence requiring fresh signatures, historical packs surviving a role-configuration change, and concurrent updates yielding a decision consistent with its signed evidence. A safety delay must remain available throughout.

### 2. Prove where confidential text can travel

A plan schema without patient fields still accepts a pasted handover note, a screenshot or a revealing project title. Opaque staff references can also be identifiable to the employer. A public roadmap, exported pack, notification, extracted attachment text and restored backup each have different readers and lifetimes. The project provides a personal-data inventory, privacy tests, structured subject export and erasure. Its DPIA records the limits of locating a name in prose, files, audit snapshots and backups. Retention remains partial. [Data flows](../../../governance/data-flow.md) · [DPIA](../../../governance/dpia.md) · [Subject-rights tests](../../../project-portfolio-management-service-with-rust/tests/requests/subjects.rs) · [Retention schedule](../../../governance/retention-schedule.md)

**Information governance lead and roadmap editor, before importing real text.** Agree the permitted fields and audiences, use an approved external reference for restricted supporting material, and put a short example of acceptable text at entry and publication. Use fictitious, distinctive text to rehearse a mistaken entry. Trace who can read it after withdrawal across the index, exports, notifications and backup lifecycle. Record which copies can be recalled, which require recipient action, who handles the incident and when retained copies expire. Require an editor to preview the actual public fields in each published language. A detector for identifier patterns could assist review, but a negative result cannot establish that a narrative is safe to publish.

### 3. Complete customer isolation and rehearse recovery of the evidence

The supplier design assigns each customer its own deployment, database, artifact store and backups. Production checks the configured deployment name. At this revision the check validates its presence and format. Binding that name to the database identity remains open under SA-21. Separately, the recovery guide gives a nightly logical-backup objective of 24 hours of potential data loss and four hours to restore service. Database and file backups are sequential. A restored decision can therefore refer to missing supporting material even if the service answers requests. [Deployment identity implementation](../../../project-portfolio-management-service-with-rust/src/deployment_id.rs) · [Supplier assurance, SA-R13](../../../spec/supplier-assurance.md) · [Recovery objectives](../../../operations/recovery-objectives.md)

**Hosting lead, before hosting a second customer or depending on a restored pack.** Complete SA-21 and test a deliberately mismatched pair of synthetic deployments. Startup, migrations and background tasks should stop before using the other customer's records. Rehearse a restore at realistic volume with a second operator. Check each sampled decision's attachment reference and content digest against the restored artifact, time the whole recovery, and have the decision owner reconcile approvals made since the backup. Agree a fallback decision channel and a named support deputy. Upstream explicitly offers no support SLA. [Restore drill](../../../scripts/restore-test.sh) · [Service commitments](../../../operations/commitments.md)

### 4. Measure whether a healthcare improvement lasted

The current benefits model gives the board a useful starting point. The proposed outcome follow-through specification adds independent effect checks (OF-2) and risk-score history (OF-3). Capture that history first. The current risk update replaces probability and impact, then records `risk_updated` with no old or new values. A subsequent dashboard cannot reliably reconstruct that trajectory. Capture score, time, actor and reason in the same transaction, label earlier history unavailable, and test every write path. The portfolio risk register can then point to a clinical hazard record held by its accountable owner. The two records answer different questions. [Risk update handler](../../../project-portfolio-management-service-with-rust/src/controllers/governance.rs) · [Proposed OF-2 and OF-3](../../../spec/outcome-follow-through.md)

**Improvement lead and analyst, for the first benefits review.** For an outpatient booking redesign, use weekly median days from accepted referral to appointment as the outcome, the proportion of eligible referrals using the new process as the process measure, and booking-team rework per 100 referrals as the balancing measure. Agree definitions with staff and patient representatives, including which referrals count, how still-waiting referrals are reported, baseline period, source, owner and review date. Read all three over time. Faster appointments for completed cases can coincide with a growing backlog. A different reviewer should be able to reproduce each figure and record a missed follow-up as unmeasured. [Institute for Healthcare Improvement guidance on establishing measures](https://www.ihi.org/library/model-for-improvement/establishing-measures)

Keep identifiable source records in the provider's analytics environment. If an interface is warranted, accept a versioned aggregate series with measure ID, period, value, unit, denominator where relevant, source revision, and an explicit missing or suppressed state. Re-importing a corrected period should preserve its provenance. For equity analysis, agree meaningful strata locally and check whether a reader could infer a small group's value from adjacent totals or successive releases. The existing utilization tests cover a small-group rule on one surface. The receiving audience and what else they know matter to disclosure risk. [Utilization request tests](../../../project-portfolio-management-service-with-rust/tests/requests/effort.rs) · [ICO guidance on effective anonymisation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-sharing/anonymisation/how-do-we-ensure-anonymisation-is-effective)

### 5. Validate the workflow with the people who must act on it

Automated web accessibility checks, table alternatives to charts and machine-drafted Welsh text are useful foundations. The accessibility statement leaves manual assistive-technology checks to the deployer. The newer Swift and Kotlin clients cover plan and task workflows. The mobile specification records partial device protections and outstanding tests for app-switcher visibility, keyboard handling and retention of record text. An ephemeral iOS transport or an Android backup exclusion establishes only one part of the device lifecycle. [Accessibility statement](../../../governance/accessibility-statement.md) · [Welsh review record](../../../governance/welsh-translation-review.md) · [Mobile scope and MA-8.8 status](../../../spec/mobile-apps.md)

**Service designer, Welsh-language reviewer and device lead.** Ask a Welsh-speaking editor and a screen-reader user to find a stale roadmap, distinguish “delay for safety” from schedule slippage, and correct a publication conflict. Record completion, interpretation errors and fixes against the text version reviewed. Before mobile rollout, use managed physical devices, the intended identity provider and synthetic plan text. Verify what remains after backgrounding, process termination, sign-out and loss of access. Start the roadmap pilot on the web so a mobile release does not become its critical dependency.

### 6. Tie procurement evidence to the release and the use case

The repository's DTAC v2 assessment identifies service 0.3.0, matcher 0.2.0 and web 0.1.0. The audited branch identifies service 0.2.0, matcher 0.2.2 and web 0.2.0, plus two unreleased 0.1.0 mobile clients. The earlier hazard analysis reports that the reviewer could not find an erasure test. The current source contains request coverage for the erasure policy. A buyer relying on either historical statement could assess the wrong build or commission work already done. [Historical DTAC assessment](../../united-kingdom/national-health-service/digital-technology-assessment-criteria/2.0/index.md) · [Historical hazard analysis, H14](../../international-organization-for-standardization/iso-14971/hazard-analysis.md) · [Current subject tests](../../../project-portfolio-management-service-with-rust/tests/requests/subjects.rs) · [Project versions](../../../AGENTS.md)

**Release manager and buyer's safety lead.** Keep the historical assessments dated. Produce a short evidence index for the candidate release covering artifact digest, component versions, intended users and decisions, test run, control owner, unresolved risk and next review. For an English deployment, document DTAC applicability with the buyer and work through the NHS clinical safety applicability questions for that workflow. Where in scope, distinguish the manufacturer's DCB0129 evidence from the deploying organisation's DCB0160 case. For a Welsh health board, agree the local assurance route and accountable clinical informatics lead. DHCW describes clinical digital safety and assurance within its own framework. Neither the existing templates nor this review supplies local sign-off. [NHS England DTAC guidance](https://digital.nhs.uk/services/digital-technology-assessment-criteria-dtac) · [Clinical safety applicability](https://digital.nhs.uk/services/clinical-safety/applicability-of-dcb-0129-and-dcb-0160/step-by-step-guidance) · [Manufacturer and deployer responsibilities](https://digital.nhs.uk/developer/guides-and-documentation/introduction-to-healthcare-technology/clinical-safety) · [DHCW clinical informatics framework](https://dhcw.nhs.wales/annual-report-2025/performance-overview/mission-5/)

The current project purpose supports an administrative pilot. A proposal to recommend care for an individual changes what must be assessed. Review the proposed function, instructions, demonstrations and marketing claims together with a qualified regulatory lead before designing or promoting it. MHRA guidance uses intended purpose in determining whether software qualifies as a medical device. A FHIR connection alone would neither establish a medical purpose nor demonstrate clinical safety. The roadmap pilot has no requirement for a patient-level interface. ## Two engineering choices that affect the wider portfolio

**Define which records belong in a decision before adding a new dashboard.** The recursive plan model makes imports and reuse easy, but registering a product for evaluation can move totals that a board reads as funded work. A repository census found that adding a bare product changed 24 of 101 views examined. Some changes are desirable, such as its appearance in the audit trail. For each board figure, publish its inclusion rule, and test an unfunded proposal, a funded rollout and a retired product against it. A health board deciding whether to buy a second prescribing product should be able to distinguish a proposal from an investment already under way. The evaluation-stage filter is a proposal at this revision. [Product evaluation evidence, PE-1 and PE-D2](../../../spec/product-evaluation.md) · [Aggregate census](../../../project-portfolio-management-service-with-rust/tests/private_aggregates.rs)

**Benchmark the reporting journey on the buyer's actual mix of plans.** In the corrected repository benchmark, a dated 12,667-task chain took a median 331 ms for a full critical-path response at one connection. The answer was 10.8 MB. A page of 100 tasks took 6 ms. The implementation already guards full responses above 5,000 tasks. Before buying more compute or rewriting the scheduler, measure the time from opening a board pack to seeing usable information, plus payload size, peak memory and errors during concurrent imports. Use representative permissions, network conditions and a realistic mix of small plans and complex programmes. Agree the acceptable time with the portfolio office before measuring it. [Corrected large-plan benchmark and measurement limits](../../../BENCHMARKS.md)

The audit also found a repeatability issue in the capacity regression gate. In the serial PostgreSQL request suite, 242 of 243 tests passed. The capacity test counted four SQL statements at five plans and six at 60. The same test passed when rerun alone against the temporary instance. Its counter measures the process total around each request. These observations establish a discrepancy, but leave the source of the two statements unresolved. Trace statements by request while running the suite, distinguish background work from the handler, and retain the small-versus-large assertion. The result does not establish a capacity limit for a deployment. [Scale regression test](../../../project-portfolio-management-service-with-rust/tests/requests/scale.rs) · [Query counter](../../../project-portfolio-management-service-with-rust/domain/src/query_count.rs)

## Evidence and limits

The review used branch source and published primary guidance. It emphasises the UK because the repository identifies NHS Wales as a prospective buyer. It examined the five applications and libraries, the database rules behind selected decisions, the tests that exercise them, governance records and the restore plan.

| Verification on the audited code | Result |
| --- | --- |
| Rust service workspace and matcher | Formatting, Clippy, workspace library tests and database-free service integration passed. The domain library reported 872 passed and one ignored, the matcher 75 passed, and the database-free integration invocation 31 passed. |
| PostgreSQL 18 integration suites | Of 243 request tests, 242 passed and one capacity-query assertion failed. It passed on an isolated rerun. All 95 tests in the other database suite passed. The load suite was excluded. |
| SvelteKit operator UI | Lint, type checking and production build passed. The 10 focused benefit and cutover view tests passed. In the full unit run the session-store file failed with local networking restricted. That file passed with loopback access (22 passed, three Redis-dependent tests skipped). All 1,534 Playwright tests passed. |
| Service-workspace line coverage | The repository reports 94.38% in its 20 November database-inclusive measurement. This audit did not remeasure coverage. Coverage establishes which lines ran and leaves clinical effectiveness and user interpretation to other methods. [Coverage method and exclusions](../../../COVERAGE.md) |

The review did not examine a running health-board deployment, patient data, real identity-provider or device policies, or a buyer's signed assurance records. It did not conduct a clinical study, independent penetration test, manual accessibility assessment or timed recovery exercise. The proposed pilot measures, owners and time boxes are recommendations. Actual patient benefit, local readiness and regulatory applicability remain decisions for the organisations responsible for the intended use.
